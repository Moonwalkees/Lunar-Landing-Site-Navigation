# 7.9 Forecast overlay controls on the 2D map

Status: done
Owner: Tony Pham
Note: done. Forecast controls, legend and hover line on the 2D map in both UIs. Added at the user's request beyond the ticket: shadows hidden while forecasting, 1 / 3 / 7 day look-aheads, an early-warning setting, and soon-to-late colour shades. Checked in the browser by the user.
Source: Extension feature (user request: near-future power/comms change heatmap)
Depends on: 7.7, 7.8

## Description
Add the forecast overlay to `frontend/src/components/TerrainMap.tsx`, which serves both UIs.

Controls, in a compact row next to `viewButtons`:
- Layer: Off / Power Δ / Comms Δ. Default is Off, so the map is unchanged unless the user turns it on.
- Mode: Δ / Worst dip
- Horizon: 3 / 6 / 12 steps. Default is 6. The label shows hours (`k × stepHours`).

Wiring:
- New `TerrainMap` props: `analysis` and `index`.
- Pass them from `board/Detail3D.tsx`, which already has `analysis` and `index`.
- Pass them from `App.tsx` (`tracks`, `index`) through `components/TerrainView.tsx`.

Hover: the existing hover readout also shows the forecast, e.g. "POWER 0.82 → 0.10 in 12 h (dips to 0.00 at +6 h)".

## Expected user interaction
The user opens the 2D map and picks Power Δ or Comms Δ, then scrubs or plays. The heatmap shows which ground is about to gain or lose the Sun or Earth link over the chosen span. The user hovers a cell for the exact numbers. Sun and Earth arrows and the site marker stay on top.

## Solution
**Chosen:**
- `frontend/src/components/TerrainMap.tsx`: new optional props `analysis` and `index`; state for layer (off / power / comms), mode (change / worst dip), look-ahead and early warning. It calls `useForecast` (7.7) and paints with `paintDelta` (7.8). The forecast only runs once the terrain grid and the analysis are both for the current site.
- Controls: a second `.actions.forecast-controls` row under the view buttons. Unselected buttons use the classic UI's `secondary` class and `aria-pressed`, which the board UI styles.
- Wiring: `board/Detail3D.tsx` passes its `analysis` and `index`; `App.tsx` passes `tracks` and `index` through `components/TerrainView.tsx`.
- Legend (`components/ForecastLegend.tsx`) at the bottom right of the map, with a line for the cell under the pointer: "Here 1.00 → 0.00 · changes at +8 h · dips to …".

Added beyond the ticket, each asked for by the user after seeing it run:
- **Shadows hidden while forecasting.** With a layer on, the base is plain relief lit from the north-west, so it no longer repaints while scrubbing.
- **Longer look-aheads.** The Ahead buttons are 3, 6 and 12 steps plus 1, 3 and 7 days, labelled in hours or days. Windows over 12 steps are sampled at about 13 moments (`sampleSteps` in `forecastCore.ts`), on multiples of a stride so neighbouring windows share frames.
- **Early warning.** A toggle that swaps the field for `marginField` (`terrain2d.ts`): 0.5 + clearance / (2 × 3°), clamped. Ground within 3° of the Sun or Earth crossing the horizon is coloured before the light or link changes. The hover line shows degrees in this mode.
- **Timing shades.** `combine` also returns `deltaAt`, the step by which half of the change has happened. `paintDelta` shades from vivid (soon) to pale (late in the span) with `deltaColour`; worst dip uses `dipAt`. The legend became two bars, Losing and Gaining, each running from "soon" to the end of the span.

Why coverage needed the two extra settings: at 12 h only 4-7% of the map changes for power and 1-4% for comms, because a cell is either lit or not and only moving shadow edges change. Only 0.1% of cells had a change too faint to colour, so it was not a colour problem. Measured at Peak near Shackleton, share of the map coloured for power: 12 h 4%, 12 h early warning 25%, 7 days 36%, 7 days early warning 62%.

Checks:
- In Node on real terrain: 18 worker and maths checks, 5 for the sampled windows (at most 14 frames per window, at most 2 new frames per playback step), 2 for the timing data and shades. The bundled worker file (3.3 kB) gives the same result as the source.
- `npm run build` passes.
- The user ran it in the browser and accepted it.

**Strengths**
- One component serves both UIs, and Off leaves the map on its old code path.
- Scrubbing costs one or two new fields per step at any look-ahead.
- The legend is built from the same colour function as the map.

**Limitations**
- Early warning changes what colour means: "the margin is shrinking", not "power will drop in this window". The legend says so.
- On long windows, worst dip can miss a drop shorter than the sampling gap (up to 14 h at 7 days).
- Short look-aheads have few distinct shades (6 at 6 steps).
- Cells on the outer edge of the map have no terrain beyond them and can show a false strip of colour.
- The 7.6 limits still apply: only the 24 km map is counted, and ridges and peaks read 0.5-0.8° too clear.
- The smoothness check was by eye; the 150 ms cold-jump figure was measured in Node (about 100 ms at 6 steps), not in the browser.

**Alternatives considered**
| Option | Why not chosen | Trade-off vs chosen |
|---|---|---|
| Stronger colours to cover more of the map | Only 0.1% of cells had a change too faint to colour | No new settings, but no real gain |
| Longer look-aheads only | Comms stays at 5-27% even at 7 days | Colour keeps one meaning |
| Forecast line in the top-right readout, as the ticket says | A second line there runs under the rover panel in the board UI | Closer to the pointer's other readout |
| Compute every step of long windows | 85 to 169 fields: 1-2 s cold, over the cache size | Worst dip would miss nothing |
| Sample long windows at `i + j × stride` | Every sample moves when `i` moves, so playback recomputes the whole window | Evenly spaced samples |
