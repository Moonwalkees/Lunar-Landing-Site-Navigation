# 7.7 Forecast frames: cache and Web Worker

Status: done
Owner: Tony Pham
Note: done. `forecastCore.ts` (maths and frame cache), `forecast.worker.ts` and the `useForecast` hook in `forecast.ts`. Tested in Node only; nothing uses the hook yet, so the in-browser smoothness check moves to 7.9.
Source: Extension feature (user request: near-future power/comms change heatmap)
Depends on: 7.6

## Description
Compute, off the main thread, how each cell's power or comms value changes over the next `k` time steps:

- **Δ:** `V(i+k) − V(i)`
- **Worst dip:** `min(V[i..i+k]) − V(i)`, which is always ≤ 0. It catches short blackouts that recover before `i+k`.

To build:
- `frontend/src/forecast.worker.ts`: holds the terrain grid and an LRU cache of per-step frames (about 32 `Float32Array`s, keyed `body:step`). Moving from `i` to `i+1` during playback computes only the one new frame, `i+1+k`.
- `frontend/src/forecast.ts`: a hook `useForecast(grid, analysis, i, k, body, mode)`. It posts requests to the worker, drops stale replies and keeps the last field until a new one arrives, so scrubbing never blocks.
- At the end of the window, `i+k` is clamped to the last step, and the hook reports the real span in hours.

## Expected user interaction
None directly. With the overlay on (7.9), the heatmap follows the scrubber and playback without stutter.

## Done when
- Scrubbing at Shackleton stays smooth with the overlay on
- A cold jump to a new index fills in within about 150 ms
- Worst-dip values are always ≤ 0
- `npm run build` passes

## Solution
**Chosen:** Three files in `frontend/src/`.
- `forecastCore.ts`: `FrameCache` (LRU of per-step fields from 7.6's `powerField` / `commsField`, 40 frames, keyed `body:step`), `combine(frames)` (now, Δ, worst dip, and the step the dip falls on) and `forecastSteps(i, k, stepCount)` (the span, cut short at the last step). No React or worker API, so it runs in Node.
- `forecast.worker.ts`: takes a `setup` message (grid and tracks, which resets the cache) and `request` messages (`id, body, i, k`). It computes one missing frame at a time and yields between frames through a `MessageChannel`. If a newer request or setup has arrived, it drops the current one; the frames already made stay cached. The four result arrays are sent as transferables.
- `forecast.ts`: `useForecast(grid, analysis, index, k, body)` returns `{ forecast, pending, failed }`. The worker exists only while `body` is not null. Replies whose id is not the newest are dropped, and the last forecast stays up while the next is pending. A new grid or analysis clears it.

Differences from the description:
- The hook takes no `mode`. Every answer carries both Δ and worst dip, so switching mode needs no recompute.
- The answer also carries `now` and `dipAt`, which the 7.9 hover readout needs.
- The maths is in a third file, `forecastCore.ts`, so the worker bundle doesn't pull in React.
- The eye height is `analysis.site.mastM`.

Checks, in Node on the Peak near Shackleton grid with a year of `/analyze` tracks (18 checks, all pass):
- Δ, worst dip and `dipAt` equal values computed directly from the 7.6 fields, for power and comms.
- Worst dip is never above 0.
- A cold k = 6 window computes 7 frames; each next step computes 1.
- The real worker code, loaded with a stand-in for the worker scope: a burst of 8 requests gets one answer, for the newest; a request made before a new setup is dropped; the span is cut short at the end of the window.
- Timing: cold jump about 90-105 ms at k = 6, next step during playback about 11-14 ms.
- At step 100, 62 cells (power) and 91 cells (comms) dip by more than 0.2 and recover by the end of the window, so worst dip does show things Δ misses.
- `npm run build` passes.

**Strengths**
- The main thread does no forecast maths, so the scrubber never waits.
- Playback costs one new frame per step, and a fast scrub only ever finishes the newest request.
- Both modes come from the same frames at no extra cost.

**Changed later, in 7.9**
- Requests and answers carry `early` (the early-warning field), and answers carry `deltaAt`, so five arrays are transferred.
- Windows over 12 steps are sampled at about 13 moments with `sampleSteps`, so a 7-day window costs at most 14 fields cold and 2 per playback step. This removes the "cold jump at k = 12 is 13 frames" concern for longer look-aheads.
- The cache holds 64 frames, and `useForecast` takes a sixth argument, `early`.

**Limitations**
- **Not run in a browser.** Nothing imports the hook yet, so Vite has not bundled the worker and the two in-browser checks ("scrubbing stays smooth", "cold jump within about 150 ms") are untested. They are now in 7.9's Done when.
- The Node test replaces `MessageChannel` with a `setImmediate` version, because Node empties a port's queue in one go and starves timers. A browser runs one task per message.
- A cold jump at k = 12 is 13 frames, about 170 ms: over the 150 ms target, which was written for k = 6.
- The whole `heights` list is copied to the worker on each new site (58k numbers, a few ms).
- If the worker cannot start, `failed` is true and there is no fallback on the main thread.

**Alternatives considered**
| Option | Why not chosen | Trade-off vs chosen |
|---|---|---|
| Compute on the main thread with the same cache | A cold jump blocks the UI for about 90 ms, and about 170 ms at k = 12 | No worker, simpler; playback would be fine, scrubbing would stutter |
| Yield with `setTimeout(0)` | Browsers add a 4 ms minimum after a few nested calls, about 50 ms on a 13-frame window | Same behaviour in Node and browsers |
| Worker computes the whole window in one go | It cannot see newer requests until it finishes, so a fast scrub queues up stale work | Simpler loop |
| Separate requests for Δ and worst dip | Both need the same frames | Slightly smaller replies |
