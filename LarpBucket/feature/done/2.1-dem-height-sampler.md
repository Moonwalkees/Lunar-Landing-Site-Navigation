# 2.1 DEM height sampler

Status: done
Owner: Aiken
Source: tech-stack.md > Stack (Terrain, Horizon algo), Build order 2

## Description
In `backend/app/horizon.py`, add `height_at(lat, lon)` (vectorised) that returns terrain height in metres with bilinear interpolation. Use the 20 m polar DEM where it covers the point, otherwise the global `LDEM_64`.

## Expected user interaction
Caller passes arrays of lat/lon; gets heights back. No visible UI.

## Done when
- Polar points read from the 20 m DEM, others from the global DEM
- Heights agree between the two DEMs within ~ tens of metres where they overlap

Note: done. `height_at` in `app/horizon.py` reads only the window it needs; polar points come from the 20 m map, the rest from the global map. Heights agree with the LOLA 5 m site tiles to about 1 m at two rim sites.

## Solution
**Chosen:** `height_at(lat, lon)` in `backend/app/horizon.py`. It takes arrays, reads only the window of the map that the points fall in, and interpolates bilinearly with numpy. Points covered by `ldem_85s_20m_crop.tif` use it; all others use `ldem_64.tif`.

**Strengths**
- Windowed reads keep memory small and make one call cheap enough for the skyline march.
- No scipy, as the stack lists only rasterio and numpy.
- Checked against the LOLA 5 m site tiles at two rim sites: about 1 m apart.

**Limitations**
- 20 m pixels cannot resolve a narrow crest. On the 37 m wide Connecting Ridge crest the yearly sunlight came out at 71% against 57% from the 5 m data at the draft coordinates.
- At the edge of the polar crop the source switches to the global map, so heights can step there.

**Alternatives considered**
| Option | Why not chosen | Trade-off vs chosen |
|---|---|---|
| Load each map fully into memory at startup | Hundreds of MB of RAM and a slow start | Faster repeated reads |
| `scipy.ndimage.map_coordinates` | scipy is not in the stack | Less code, and cubic interpolation if wanted |
| Nearest pixel | Stair-steps the skyline near the site | Slightly faster |
