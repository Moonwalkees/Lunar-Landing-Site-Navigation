# 4.11 2D bird's-eye terrain view

Status: done
Owner: Maddie
Source: not in scope.md yet. Lighter alternative to the 3D terrain view (4.9, 4.10, `doc/3d-view.md`). Supports scope.md > Core 3 Horizon panorama and Core 5 (time scrubber). Needs the team's agreement, as 4.9 did.
Depends on: 4.9, 4.10
Note: done. New `GET /terrain` height grid; `TerrainMap.tsx` draws relief, shadows and Sun/Earth arrows; `TerrainView.tsx` offers **Bird's-eye view** (default) alongside **Orbit view** and **Surface view**, and lazy-loads the Unity view only for orbit or surface. See `doc/2d-view.md`.

## Description
Add a 2D top-down (bird's-eye) view of the terrain around the selected site, as a cheaper option alongside the 3D view. The 3D view adds a 68 MB Unity WebGL build and needs a GPU. It has not been tested on a weak laptop or a phone. The 2D view should load in a fraction of that and run smoothly on low-end devices.

The view shows:
- The LOLA heights around the site as a shaded relief or height map, north up, with a scale bar
- A marker at the site
- The Sun and Earth directions (azimuth) as arrows or edge markers, with their elevation in a label
- Optionally, which ground is in shadow at the current time, if it can be computed cheaply on a coarse grid

Like the 3D view, it only displays the Sun and Earth angles it is given from `POST /analyze` at the scrubber's time index. It never computes them itself.

Keep it light. Use what is already in the stack (for example a Plotly heatmap or a plain `<canvas>`), not a new 3D engine. Use a downsampled height grid or pre-rendered image of the existing DEM crops (1.3), not the full-resolution tiles.

## Expected user interaction
The terrain panel offers **Bird's-eye view** alongside the existing **Orbit view** and **Surface view** buttons, and opens on bird's-eye. In 2D the user sees a top-down map of the area around the site with the site marked and Sun and Earth direction indicators. Dragging the scrubber moves the indicators (and shadows, if included) in step with the panorama and time series. The user can pan and zoom. The 3D build is only downloaded when the user switches to 3D.

## Done when
- `npm run build` passes
- Bird's-eye is a view option next to orbit and surface, and is the default
- In 2D, the Unity build is not downloaded (check the browser network tab)
- The 2D view's total download is well under the 3D view's (target: under 5 MB per area)
- The scrubber moves the Sun and Earth indicators in the 2D view, in step with the panorama
- A site outside the DEM coverage shows a message, not a wrong location
- Notes added to `doc/3d-view.md` (or a new `doc/2d-view.md`)

## Solution
**Chosen:** The backend sends a small north-up height grid and the browser draws it on a plain `<canvas>`.
- `GET /terrain?lat=&lon=` (`backend/app/main.py`) returns 241 x 241 heights at 100 m from `terrain_grid()` in `backend/app/horizon.py`. It walks out along great circles from the site exactly as `skyline()` does, so north and the azimuths match the panorama. Gzipped by `GZipMiddleware`: about 96 kB per site.
- `frontend/src/terrain2d.ts`: `relief()` hillshade (once per grid) and `sunlight()`, which gives each cell the share of the Sun's disc it sees by marching toward the Sun over the curved surface (10-15 ms per Sun position).
- `frontend/src/components/TerrainMap.tsx`: canvas map with site marker, Sun and Earth arrows, north arrow, scale bar, wheel zoom, drag pan, double-click reset and a hover readout. Fetches are debounced and cached per site.
- `frontend/src/components/TerrainView.tsx` is now the panel and owns the view buttons: **Bird's-eye view** (default), **Orbit view**, **Surface view**. Orbit and surface moved out of the 3D component, which is now `TerrainView3D.tsx` with a `view` prop, loaded with `React.lazy`. The Unity loader and build are not requested until orbit or surface is picked, and switching between orbit and surface keeps the same Unity instance (checked in headless Chromium).
- Tests: `backend/tests/test_terrain.py` (grid centred, north up, east right). Notes in `doc/2d-view.md`; `doc/3d-view.md` updated for the rename.

**Strengths**
- About 100 kB per site instead of 68 MB, and no GPU or WebGL needed.
- Works for any site: 20 m polar map near the south pole, global 474 m map elsewhere. The 3D view only covers four areas.
- At the site, map shadows agreed with `POST /analyze`'s Sun fraction at 99-100% of 2-hour steps over 29.5 days for all five presets.
- Reuses the backend's height sampling and geometry, and only displays the Sun and Earth angles from the analysis.

**Limitations**
- Only terrain inside the 24 km square casts shadows. Ridges further out (the analysis looks to 150 km) are missed, so cells near the edge can look lit when they are not.
- Ground-level observer (no 2 m mast) and 100 m cells, so small features don't show.
- Not in scope.md yet; needs the team's agreement, as 4.9 did.
- No pinch zoom. Not tested on a real phone.
- "Outside DEM coverage" can't happen with the global map behind it; errors from the backend show as a message in the panel.

**Alternatives considered**
| Option | Why not chosen | Trade-off vs chosen |
|---|---|---|
| Pre-rendered images per area in `frontend/public/` | Static shadows can't follow the scrubber, and only the four 3D areas would be covered | No backend change; no compute in the browser |
| Plotly heatmap | Redrawing ~58k cells through Plotly on every scrubber step is heavier than a canvas `putImageData` | Free axes, hover and zoom |
| Shadows on every other cell, then interpolated | Built first (~4 ms): shadow edges looked blocky | 3x faster |
| Separate **2D / 3D** switch above orbit / surface | First version; the owner preferred one row of view buttons | Made the 2D vs 3D cost choice more explicit |
| Shadows computed in the backend per time step | One request per scrubber step, or a large precomputed stack | Could use the full 150 km horizon |
