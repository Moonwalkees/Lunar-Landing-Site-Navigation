# 4.29 Remember the user's setup between visits

Status: done
Owner: Maddie
Note: Board and classic setups are saved in localStorage (src/persist.ts) and restored on load; RESET next to RUN clears them.
Source: doc/scope.md > Core 1 (custom sites), Core 3 (rover numbers); doc/tech-stack.md > Frontend (client state); user request 2026-11-15

## Description
Everything the user sets up is lost on reload, and on the CLASSIC VIEW / BOARD VIEW switch, which reloads the page (4.22). Keep it in the browser's `localStorage` so it comes back: on the board, the custom sites, the presets the user deleted, the mission window (start, days, step) with its rover numbers, the selected site and the sort order; on classic, the site form (site, window and rover). No backend or accounts: this is per browser only.

## Expected user interaction
The user adds a custom site, deletes a preset and runs a different window with their own rover numbers. They reload, or flip to the classic UI and back, and find the same board. A RESET button next to RUN clears what was saved and returns to the defaults.

## Done when
- Board: custom sites, deleted presets, the window and rover the user ran, the selected site and the sort order survive a reload
- Classic: the site form (site, window, rover) survives a reload
- A window the user never ran is not saved, so the default start date stays "today" on every visit
- Saved data is checked on load; bad or old data is ignored, never crashes the app
- Works when browser storage is blocked (the app behaves as before)
- RESET clears the saved setup and restores the defaults
- `npm run build` passes

## Solution
**Chosen:** `frontend/src/persist.ts` reads and writes two `localStorage` keys, `lunar-board-v1` and `lunar-classic-v1`, and validates every field on load (types, lat/lon ranges, the same rover and window limits as the forms and backend, known sort keys, unique `c:` custom ids); anything invalid is dropped, never thrown on. `src/board/BoardApp.tsx` loads it once, seeds its state from it (custom sites, deleted presets, window and rover, selected site, sort order), and saves in one `useEffect`. `src/App.tsx` does the same for the classic site form. A RESET chip beside RUN in `Mission` (`src/board/Panels.tsx`) calls `clearSaved()` and reloads. Checked with a scratch script against a fake `localStorage` (round trip, bad fields, junk JSON, blocked storage, reset) and `npm run build`.

**Strengths**
- Per browser, no backend, no accounts, so it fits the agreed stack (client state) and the deploy needs no change.
- The window is saved only after the user presses RUN, and the selected site only after they pick one, so the default start date stays "today" and the backend's default site is not frozen in.
- Storage failures (private window, site data off) fall back to the old behaviour. `sites` can never be empty: saved deletions that would empty the board are ignored.
- Survives the board/classic switch, which reloads the page (4.22).

**Limitations**
- Not shared between browsers or devices, and cleared when the user clears site data.
- Saved window and custom sites are not re-checked against the backend's current presets; a saved selected preset that no longer exists falls back to the first site.
- Classic's pinned compare sites and the board's playback speed and open panels are not saved (pins carry computed metrics that would go stale).
- Not exercised in a real browser session in this ticket, only through the parser script and the production build.

**Alternatives considered**
| Option | Why not chosen | Trade-off vs chosen |
|---|---|---|
| Save in the backend (database, user accounts) | Out of scope in scope.md and tech-stack.md; adds login and storage | Would follow the user across devices |
| Encode the setup in the URL | Long, and custom sites with rover numbers do not fit nicely; the UI switch already uses `?ui=` | Shareable links (see 8.1), nothing stored locally |
| Save the whole `win` on every load | Freezes the default start date, so a returning user sees a stale window | Simpler code |
| Persist playback speed and pinned compare sites | Pins hold computed metrics that go stale; speed is minor | More "complete" restore |
