# 5.2 Host the backend

Status: done
Owner: Maddie
Source: tech-stack.md > Stack (Hosting)
Depends on: 5.1
Note: Backend live on Dokploy at space-backend.universal-approximation.com, with CORS set for the frontend origin.

## Description
Deploy the Docker image to Render or Fly.io. Set CORS to allow the deployed frontend origin.

## Expected user interaction
Anyone can hit `https://<backend-url>/sites`.

## Done when
- Public URL responds; `/analyze` works within the host's memory limit

## Solution
**Chosen:** Hosted on Dokploy (not Render/Fly) from `backend/Dockerfile` (Build Path `/backend`, container port 8000) at `https://space-backend.universal-approximation.com`. `FRONTEND_ORIGINS=https://space.universal-approximation.com` is set as a normal runtime env var, which `app/main.py` adds to the CORS allow-list. `/sites`, `/terrain` and `/analyze` all return 200 from the public URL, with the right `access-control-allow-origin` header.

**Strengths**
- Same Dockerfile works on any container host; nothing is Dokploy-specific.
- The kernels and DEMs are baked into the image at build time (see 5.4), so the container needs no volume and starts in seconds.

**Limitations**
- `doc/tech-stack.md` still says Render/Fly for the backend; it has not been updated to match.
- First build downloads the kernels from NAIF each time the data layer is rebuilt; later builds reuse Docker's layer cache.
- Memory use under the host's limit was not measured, only that `/analyze` returns 200 for a 30-day run.

**Alternatives considered**
| Option | Why not chosen | Trade-off vs chosen |
|---|---|---|
| Render / Fly.io (as in tech-stack.md) | The team already runs a Dokploy server. | Managed hosting with less to maintain, but extra cost and a second platform. |
| Bind-mount the data folder from the server | Ties the data to one machine and needs a manual `rsync` after any rebuild. | Fast to start, but not repeatable; replaced by R2 in 5.4. |
