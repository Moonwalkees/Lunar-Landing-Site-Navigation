# 1.2 Sun and Earth az/el from a lunar surface point

Status: done
Owner: Tony Pham
Source: scope.md > Data (Sun/Earth azimuth and elevation), tech-stack.md > Stack (Ephemeris)
Note: `sun_earth_azel(lat, lon, times)` in `backend/app/ephemeris.py` (lat/lon in degrees; az/el returned in **radians**, az [0, 2π) from north clockwise, to match the 3.1 power model), all SPICE calls under `SPICE_LOCK` (CSPICE isn't thread-safe); 16 tests in `backend/tests/test_ephemeris.py`. Measured tolerances: Apollo 11 Earth el 66° mean, 58-73° over a month; south pole Earth el within ±7.1°.

## Description
In `backend/app/ephemeris.py`, add `sun_earth_azel(lat, lon, times) -> dict` that returns Sun and Earth azimuth (deg, from north, clockwise) and elevation (deg) for each UTC time. Use `spiceypy.spkcpo` with the observer fixed on the Moon in `MOON_ME`, then rotate into local east/north/up.

## Expected user interaction
Caller passes a site and a list of times; gets back arrays `sun_az, sun_el, earth_az, earth_el` of the same length.

## Done when
- At the subsolar point the Sun elevation is ~90°
- Earth elevation at Apollo 11 (0.67°N, 23.47°E) is high (~65°) and almost constant over a month
- Earth elevation at the south pole stays within a few degrees of 0° (libration wobble)

## Solution
_Backfilled on 2026-11-14 from the code and its comments, after the ticket closed. The original owner should correct anything that differs from their actual reasoning._

**Chosen:** `backend/app/ephemeris.py` builds the site on the mean-radius sphere in `MOON_ME` (`latrec` with the PCK radius). It gets apparent directions to the Sun and Earth with `spkcpo` (observer fixed on the Moon, `LT+S` correction) and projects them onto a local east/north/up frame to get azimuth (from north, clockwise) and elevation. All SPICE calls run under a module-level `SPICE_LOCK` (an `RLock`), and kernels load once, lazily or at app startup.

**Strengths**
- `spkcpo` handles the Moon's rotation and light time in one call, so the code does no manual frame or time handling.
- `LT+S` gives where the body appears in the sky, which is what shadowing and line of sight need.
- Small, separately testable pieces (`local_enu`, `azel`, `body_directions`). The azimuth convention is written down for `horizon.py` to match.
- The lock makes the module safe under FastAPI's threadpool. CSPICE is not thread-safe and `spiceypy` releases the GIL.

**Limitations**
- Elevation is against a smooth sphere. Terrain is left to `horizon.py`, and site height above the mean radius is ignored.
- One `spkcpo` call per time step in a Python loop, under one global lock, so long ranges at fine steps are slow and requests run SPICE one at a time.
- At the exact poles "north" is defined along the given longitude's meridian, so azimuths there depend on `lon`.
- Tolerances are measured, not exact: Apollo 11 Earth elevation is 58-73° over a month (mean 66°) and the south pole stays within ±7.1°.

**Alternatives considered**
| Option | Why not chosen | Trade-off vs chosen |
|---|---|---|
| `spkpos` from the Moon's centre plus a site offset | Needs manual light-time and frame-rotation handling | Same result with more code and more ways to get it wrong |
| `azlsta` (SPICE's built-in az/el) | Its own azimuth and sign conventions would have to match `horizon.py` | Fewer lines, but the convention is hidden |
| Skyfield or astropy | Tech stack fixes SPICE with the DE440 / `MOON_ME` kernels | Friendlier API, but weaker lunar body-fixed frame support |
| Per-thread or per-process SPICE instead of a lock | More complex; not needed at current load | Parallel requests, at the cost of memory and startup time |
