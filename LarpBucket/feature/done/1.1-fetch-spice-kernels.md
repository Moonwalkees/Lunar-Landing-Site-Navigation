## Description
Write `backend/scripts/fetch_data.py` (kernel part) to download the NAIF kernels into `backend/data/kernels/`: `de440s.bsp`, `moon_pa_de440_200625.bpc`, `moon_de440_250416.tf`, `naif0012.tls`, `pck00011.tpc`. Skip files that already exist. Add a `backend/data/kernels/meta.tm` metakernel listing them.

## Expected user interaction
Developer runs `python scripts/fetch_data.py kernels` once; files appear in `backend/data/kernels/`. Running it again does nothing.

## Done when
- All 5 kernels + `meta.tm` present
- `spiceypy.furnsh("meta.tm")` loads without error
- `backend/data/` is gitignored

## Solution
_Backfilled on 2026-11-14 from the code and its comments, after the ticket closed. The original owner should correct anything that differs from their actual reasoning._

**Chosen:** A stdlib-only CLI, `backend/scripts/fetch_data.py`, with an `argparse` subcommand per dataset (`kernels` now, `dems` in 1.3). Each kernel downloads to a `.part` file that is renamed only when complete, and existing files are skipped. The script writes `meta.tm` with an absolute `$KERNELS` path, split into 70-character pieces with SPICE's `+` continuation, and rewrites it only when its contents change.

**Strengths**
- Safe to re-run: an interrupted download leaves no half-written kernel that a later run would skip.
- No extra dependencies (`urllib`, `shutil`), so it runs before `requirements.txt` is installed.
- An absolute path means `furnsh("meta.tm")` works from any working directory. SPICE resolves relative paths against the process cwd, not the metakernel's folder.
- The subcommand layout gives 1.3 an obvious place to add DEM fetching.

**Limitations**
- `meta.tm` has the machine's absolute path baked in, so it has to be regenerated after moving the repo or copying `data/` into a container (relevant to 5.1). Re-running the script does this.
- No checksum check. A file that downloads fully but is wrong (for example an HTML error page with a 200 status) is kept and skipped on later runs.
- Downloads run one after another with no retries.

**Alternatives considered**
| Option | Why not chosen | Trade-off vs chosen |
|---|---|---|
| Commit kernels to git | About 30 MB of binaries in history | No fetch step, but slower clones and harder kernel upgrades |
| Relative paths in `meta.tm` | Break unless the process cwd is `kernels/` | Portable file, but fragile at runtime |
| Furnish each kernel from Python, no metakernel | Ticket asks for `meta.tm`; spreads the kernel list into app code | No path issue, but other tools can't load the same set |
| `requests` with a progress bar | Extra dependency for a one-off script | Nicer output only |
