# 7.12 Forecast overlay: rough while moving, sharp when still

Status: done
Owner: Tony Pham
Note: done. The worker keeps a half-resolution grid and cache; the hook asks for a rough field at once and the sharp one after 200 ms of stillness. Tested in Node; not yet seen in a browser.
Source: Extension feature (user request, follow-up to 7.7 and 7.9). `doc/2d-view.md` > Forecast overlay > Speed.
Depends on: 7.9

## Description
Each forecast field costs about 13 ms because it visits all 58,000 cells of the 100 m grid. While the timeline is moving, that detail is wasted: the picture is replaced within a moment.

Make the overlay adapt:
- While the user scrubs or plays, the worker computes on a half-resolution grid (every second cell, 200 m, 121×121), which costs about a quarter as much per field.
- Once the timeline has been still for a moment (about 200 ms), the worker recomputes at full resolution and the map swaps it in.
- The rough field is drawn through the same smooth upscaling as the sharp one, so the two line up on the map.

The rough grid is more optimistic on ridges than the 100 m grid (see 7.6), so it is only ever a preview: the sharp field always replaces it when the timeline stops.

## Expected user interaction
The user scrubs or plays with the forecast on. The heatmap follows more smoothly and looks slightly softer. When they stop, it sharpens within a moment, with no jump in position.

## Done when
- A rough field costs about a third or less of a sharp one
- The sharp field replaces the rough one after the timeline stops, and is identical to today's
- Rough and sharp line up on the map (no shift)
- Hover values still read correctly while the rough field is showing
- `npm run build` passes

## Solution
**Chosen:**
- `frontend/src/forecastCore.ts`: `halfGrid(grid)` takes every second cell (241 → 121 a side, 200 m). With an odd size the edges and the centre fall on the full grid's.
- `frontend/src/forecast.worker.ts`: a second `FrameCache` over the half grid. Requests carry `rough`; answers carry `rough` and `size` (cells per side).
- `frontend/src/forecast.ts`: on any change (time step, look-ahead, layer, early warning) `useForecast` asks for a rough field at once and sets a 200 ms timer (`SETTLE_MS`) for the sharp one; a further change cancels the timer. `pending` stays true until the sharp answer.
- `frontend/src/terrain2d.ts`: `upsampleAxis(n, fieldN)` maps image pixels onto a coarser field whose first and last cells sit on the grid's, so `paintDelta` draws a rough field in the same place as a sharp one.
- `frontend/src/components/TerrainMap.tsx`: accepts a field smaller than the grid and scales the hover lookup to it.
- `doc/2d-view.md` > Forecast overlay > Speed has a line on it.

Checks, in Node on the Peak near Shackleton grid:
- A rough field takes 4.1 ms against 24.8 ms sharp in the same run (6× faster; four times fewer cells, and shorter sweeps).
- The base map and a full-size overlay paint byte-for-byte as before.
- One changed cell given at full size and as its half-size counterpart lands on the same image pixel (320.5, 160.5).
- Rough and sharp agree on losing / gaining / no change at 96.5-98.5% of cells, across 12 h and 7 day spans, power and comms, with and without early warning.
- The worker answers a cold jump rough in 26 ms and then sharp in 100 ms.
- The 18 earlier worker and maths checks still pass, and `npm run build` passes.

**Strengths**
- The map follows the scrubber sooner, and what is on screen at rest is exactly the 7.9 result.
- All of it is inside the worker, the hook and one paint helper; no new controls.
- The same switch would make a finer resting grid practical (proposed 7.11: 50 m when still).

**Limitations**
- Not seen in a browser: the softness of the rough field and the swap to sharp have only been checked on rendered images.
- The rough grid reads more optimistic on ridges and peaks than the 100 m grid (see 7.6). It never stays on screen once the timeline stops.
- Every change now costs a rough pass as well as the sharp one, so a single click computes slightly more in total.
- During slow playback (more than 200 ms a step) each step shows rough then sharp, which may flicker slightly.
- Every second cell is taken as it is, not averaged, so a one-cell feature on a skipped row is missed in the preview.

**Alternatives considered**
| Option | Why not chosen | Trade-off vs chosen |
|---|---|---|
| Drop to rough only when the device is slow (time each field) | The user chose rough-while-moving; it can be added on top later | Fast devices would stay sharp while moving |
| A Fast / Fine button | Puts the decision on the user | Simplest to build |
| Average 2×2 cells for the half grid | The half grid's cells would sit between the full grid's, so the two would not line up | Smoother preview |
| Rough only for time-step changes, sharp at once for other changes | A cold sharp window is about 100 ms; rough first answers in about 26 ms | One fewer pass on a click |
