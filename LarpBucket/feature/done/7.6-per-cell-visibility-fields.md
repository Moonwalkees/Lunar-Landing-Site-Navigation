# 7.6 Per-cell horizon, power and comms fields

Status: done
Owner: Tony Pham
Note: done. `horizonToward`, `earthLink`, `powerField` and `commsField` added to `terrain2d.ts`; `sunlight()` is unchanged. The centre-cell check against `/analyze` only partly passes: the 100 m grid reads 0.5-0.8° too clear on ridges and peaks. Accepted for now by the user (see Limitations, and proposed 7.11).
Source: Extension feature (user request: near-future power/comms change heatmap). Builds on doc/2d-view.md and the scope.md > Core 4 model (Sun disc fraction, Earth margin thresholds).
Depends on: BUG-010 (fast shadow pass)

## Description
The forecast heatmap (7.7 to 7.9) needs a power value and a comms value for every cell of the `GET /terrain` grid at any time step. Today only `sunlight()` in `frontend/src/terrain2d.ts` exists, and it gives the Sun only. Split its terrain march into a reusable horizon pass and build both fields on it:

- `horizonToward(grid, az, el): Float32Array`: the local horizon elevation in degrees per cell, looking along `az`, with curvature included. It uses the fast sweep from BUG-010.
- `sunlight()` becomes a wrapper over `horizonToward` and returns the same output as today.
- `earthLink(grid, az, el): Float32Array`: `clamp(margin / 0.5°, 0, 1)`, where `margin = el − horizon`. On this scale 0 is blocked, 0 to 1 is marginal and 1 is clear, matching the scope.md thresholds.
- `powerField(grid, sun, behindEarth)` returns the Sun disc fraction × (1 − behindEarth). `commsField(grid, earth)` returns `earthLink`.

Both fields run from 0 to 1, so the heatmap can use one colour scale for both. The Sun and Earth az/el come from the `/analyze` response and apply to the whole 24 km grid.

## Expected user interaction
None visible. The 2D map looks exactly as before. Callers pass a grid and a Sun or Earth az/el and get back an n×n `Float32Array`.

## Done when
- `sunlight()` output matches the old version (max abs diff < 0.01) on the Shackleton grid
- At the centre cell, `earthLink` agrees with `/analyze` `comms[t]` for most steps. Differences are expected only where terrain beyond 12 km is the blocker
- `npm run build` passes

## Solution
**Chosen:** All in `frontend/src/terrain2d.ts`.
- `horizonToward(grid, az, eyeM = 0)`: horizon elevation in degrees per cell, a thin wrapper over the BUG-010 sweep (`horizonTangent`). It takes no `el`, unlike the description: the horizon doesn't depend on the body's elevation.
- An internal `clearance(grid, az, el, eyeM)` gives the body's elevation minus the horizon per cell, including the tilt of the ground with the Moon's curvature. `sunlight()` and `earthLink()` are both one-line ramps over it.
- `earthLink(grid, az, el, eyeM = 0)`: `clamp(clearance / MARGINAL_COMMS_DEG, 0, 1)`, with `MARGINAL_COMMS_DEG = 0.5` as in the backend.
- `powerField(grid, sun, behindEarth = 0, eyeM = MAST_M)` and `commsField(grid, earth, eyeM = MAST_M)`.
- **Added beyond the ticket:** an eye height. The two fields look from `MAST_M = 2` m above the ground, the same as the backend's `MAST_M` in `/analyze`. Without it, a cell was blocked by ground 100 m away that the rover's mast sees over (2 m at 100 m is over 1°). `sunlight()` keeps `eyeM = 0` by default, so the map's ground shadows are unchanged.

Checks, run in Node on the real `GET /terrain` grids:
- `sunlight()` against the BUG-010 version at 8 Sun positions: max abs diff 2×10⁻⁶ (float32 rounding).
- `npm run build` passes.
- Centre cell against `/analyze` for all six presets, one year at 6 h steps (1461 steps):

| Site | Comms state agrees | Sun lit/unlit agrees | Cause of comms mismatches |
|---|---|---|---|
| Shackleton crater floor | 100% | 100% | none |
| Apollo 11 | 100% | 100% | none |
| Apollo 17 | 100% | 99.5% | none |
| Malapert Massif | 93.6% | 92.5% | 94 steps, all terrain beyond the grid |
| Peak near Shackleton | 95.7% | 87.8% | 63 steps: 7 far terrain, 56 grid resolution |
| Connecting Ridge | 85.6% | 85.0% | 211 steps, all grid resolution |

"Grid resolution" means the backend's own skyline, cut off at 12 km, disagrees with the grid. In every mismatch the grid's horizon is the lower one.

**Strengths**
- One horizon pass serves Sun and Earth, about 13 ms per body per time step, with no backend change.
- Both fields are 0 to 1, and comms ramps through the marginal band, so one colour scale fits both and a link shows as weakening before it drops.
- Same mast height and thresholds as `/analyze`, so the fields and the site's own numbers mean the same thing.

**Limitations**
- **The 100 m grid reads too clear on ridges and peaks.** It misses small rises within about 100 m of the rover that the backend's 20 m data sees, so the horizon comes out 0.5-0.8° too low at Peak near Shackleton and Connecting Ridge. That is as large as the whole marginal band. The user accepted this for now: the heatmap shows change between steps and every cell carries the same bias. A 50 m grid roughly halves it (see the table below and proposed ticket 7.11).
- Only terrain inside the 24 km grid counts. `/analyze` looks out to 150 km, which is the cause of every Malapert mismatch.
- The Sun and Earth az/el are the site's, applied to the whole grid apart from the curvature tilt.
- The Earth is treated as a point at its centre, as in scope.md.

**Alternatives considered**
| Option | Why not chosen | Trade-off vs chosen |
|---|---|---|
| 50 m grid from `GET /terrain` | Four times the cells: each pass goes from about 13 ms to about 50 ms, and the download needs a binary format. Deferred to proposed 7.11 | Comms agreement rises from 95.4% to 99.2% at Peak near Shackleton and from 85.2% to 92.3% at Connecting Ridge; bias drops from -0.49° to -0.11° and from -0.80° to -0.38° |
| Heights sent in centimetres, not whole metres | Tested: no real change (bias -0.45° against -0.49°) | Larger response for nothing |
| No eye height (look from the ground) | Cells were wrongly blocked by the next cell over; `/analyze` uses a 2 m mast | Simpler signature, wrong near-field |
| Per-cell fields from the backend (a skyline per cell) | About 1 s per skyline, 58k cells | Would match `/analyze` exactly, far too slow without precompute |
