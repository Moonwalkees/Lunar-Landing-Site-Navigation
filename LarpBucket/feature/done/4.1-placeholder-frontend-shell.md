## Description
React + Vite + TS app in `frontend/` with placeholder panels: site form, metric cards, panorama, time series with scrubber, compare (up to 4). No API calls, no moon data.

## Expected user interaction
`cd frontend && npm run dev`, open http://localhost:5173. Pick a preset or type lat/lon, set dates, drag the scrubber, add sites to compare. All values show `—`.

## Done when
- Builds with `npm run build`
- All five panels render

Note: done. Panels in `frontend/src/components/`, data shapes in `frontend/src/types.ts`.

## Solution
_Backfilled on 2026-11-14 from the code and its comments, after the ticket closed. The original owner should correct anything that differs from their actual reasoning._

**Chosen:** A React + Vite + TypeScript app in `frontend/`. `App.tsx` holds all state with plain `useState` and passes it into five presentational components in `frontend/src/components/`. Data shapes (`SiteInput`, `Metrics`, `PinnedSite`) and `EMPTY_METRICS` are in `frontend/src/types.ts`, and presets are in `frontend/src/sites.ts`. `analyze()` is a stub that resets the metrics.

**Strengths**
- Matches the agreed stack (React, Vite, TS, plain `useState`), with no state library to learn.
- Fixing the types first gives 4.2 (API client) a clear target. Panels only need real data in place of `EMPTY_METRICS`.
- Each panel is its own file, so 4.3-4.6 can be worked on in parallel by different people.

**Limitations**
- Presets are hard-coded until 4.3 loads them from `GET /sites`.
- The scrubber range is computed in the client (`days * 24 / stepHours`), which breaks on `stepHours = 0` (BUG-002). Pinned sites keep a stale scrubber index (BUG-001).
- Unstyled. The restyle is 4.8.

**Alternatives considered**
| Option | Why not chosen | Trade-off vs chosen |
|---|---|---|
| A state library (Redux, Zustand) | Tech stack says plain `useState`; the state is small | Easier to share state later, but more setup now |
| Build the panels with real API calls straight away | Backend didn't exist yet | Less rework, but frontend work would be blocked on the backend |
| Next.js | Not in the stack; no SSR need for a single-page tool | Routing and SSR the app doesn't use |
