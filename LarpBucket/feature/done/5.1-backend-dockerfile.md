## Description
Write `backend/Dockerfile`: Python slim image, install requirements, copy app + kernels + cropped DEMs, run uvicorn on `$PORT`.

Data notes (from 1.1/1.3): copy only `data/kernels/` (~44 MB) and the two GeoTIFFs in `data/dem/`. Exclude `data/dem/raw/` (~1 GB of source PDS files, present only after `fetch_data.py dems --keep-raw`) via `.dockerignore`. `meta.tm` holds an absolute path, so regenerate it inside the image with `python scripts/fetch_data.py kernels` (it skips the existing kernels and only rewrites `meta.tm`).

## Expected user interaction
`docker build` and `docker run -p 8000:8000` serve the API locally.

## Done when
- `GET /sites` and `POST /analyze` work from the container

## Solution
**Chosen:** `backend/Dockerfile` uses `python:3.14-slim`, installs `libexpat1` and `requirements.txt`, copies the app, scripts, kernels and the two prepared GeoTIFFs, then runs `fetch_data.py kernels` to regenerate `/app/data/kernels/meta.tm`. Uvicorn binds to `0.0.0.0` on `$PORT` (default 8000), with `exec` forwarding stop signals. `backend/.dockerignore` excludes raw DEM downloads, partial downloads and development files. `README.md` documents data preparation, build, run and API checks.

**Strengths**
- Reuses prepared datasets without downloading and cropping the full DEMs during each image build.
- Copies dependencies before application code for Docker layer reuse; runtime needs no network or data mounts.
- Built `lunar-backend:feature-5.1` successfully. Live HTTP checks inside the container returned five presets and successful polar/Apollo 11 analyses (49 time samples, 720 skyline points and 12 metrics).
- Verified both endpoints with `PORT=8080` and `--network none`; confirmed the regenerated kernel path and absence of raw DEMs and the local virtual environment.

**Limitations**
- Prepare the gitignored datasets with `fetch_data.py kernels` and `fetch_data.py dems` before building on another machine. The build context includes about 417 MB of data.
- Uses the existing unpinned requirements; future builds may resolve different dependency versions. Hosting is covered by ticket 5.2.

**Alternatives considered**
| Option | Why not chosen | Trade-off vs chosen |
|---|---|---|
| Download and crop data in a separate Docker build stage | Ticket specifies copying prepared data; full source downloads make clean builds slower and dependent on NASA/PDS availability | Would remove local data preparation but repeat expensive data work on clean builds |
| Mount datasets at runtime | Hosting plan calls for datasets inside the image | Smaller image but requires separately provisioned persistent storage |
